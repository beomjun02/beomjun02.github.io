Overview

[TL;DR] The val loader never left arctic, so every result this project has reported was measured on 32–48 chunks of one dataset; restated properly the ranking survives but nothing beats a zero predictor, every architecture addition we tried is null or negative, and the only real levers are data composition and training length.

  • Found: build_loader gates every sampler on split=="train", so val walks the chunk index in file order — the first 400 batches are 100 % arctic.
  • Fixed and restated: a stratified six-dataset evaluator, validated to reproduce the old probe digit-for-digit on the old 48 chunks; 18 historical checkpoints rescored.
  • Settled: nine ablations re-tested with a paired bootstrap — only three were ever distinguishable from their control. Eight new arms this session: all architecture additions null or negative.
  • New: a model trained only on human hands keeps 79 % of its hand direction accuracy on the Sharpa hand, zero-shot; 10 % co-training buys +0.014 on the robot at no cost on the human.
  • And the base now works: the recommended configuration plus one data decision reaches ADE 7.71 against a 7.97 zero predictor at 50,000 steps — the first model in this project to beat predicting nothing on a real evaluation, winning on four of six datasets.

Method (1): what the evaluation was actually measuring

Val has 41,907 chunks over six datasets; evaluate() saw the first 32, and they are all arctic.

  • Every sampler in build_loader is gated on split == "train"; val therefore iterates the index in file order, and find_manifests sorts alphabetically.
  • The probe that produced the whole scoreboard, dir_mag_split_c.py --batches 6, saw the first 48 chunks. The first 400 batches are arctic.
  • arctic is atypical: two hands plus one large articulated object, second-richest in contact (6.9 % of points within 1 cm), smallest scenes (52 cm).

Method (2): what was tried, and how it was judged

Two architecture components aimed at the interface, three data-composition arms, each with its own control.

  • Measured before designing: the hand–object interface is 2.7 % of points, but only 5.8 % of k=8 patches mix a contacting with a non-contacting point — so this is capacity allocation, not resolution.
  • i1 interface tokens (128 nearest cross-entity points as k=1 tokens, zero-init residual) · i2 spatial RoPE over (t,x,y,z) · i3 both · i4 uniform k=4 as the token-count control.
  • i5 drop hot3d · i7 drop hot3d+dexycb · i8 a random 68 % of episodes, the data-volume control · i9 10 % Sharpa co-training.
  • Judged by paired bootstrap over the same stratified chunks, at matched step counts — not by the in-training curve.

Discussion & action items

Stop adding architecture. The configuration that works is the plain one; spend the compute on data curation and training length.

  • Keep: video-DiT over (frame × patch) tokens · k=8 part-major Hilbert patches (k=4 worse, k=16 null) · full 3-D attention (PTv3 windows −0.097) · v-parameterisation · time-RoPE only · history H=2 (+0.044, the one architectural lever that ever paid) · no auxiliary losses (rigidity −0.018) · 512 pts/entity, T=10 @10 Hz.
  • Ranked levers: ① training length (109k → 0.248 vs 10k → 0.183) ② history +0.044 ③ data composition +0.008 ④ everything else null or negative.
  • Discussion — the interface is 2.7 % of points and therefore 2.7 % of the loss; structural fixes did not reach it. Options: (a) accept it and buy length, (b) weight the loss at contact — which breaks the "flow loss only" decision. Recommend (a) until the base model beats zero.
  • Action items — ① val_stratified on for every new run (implemented, default off so runs in flight keep their basis) · owner: me · done ② long run of the recommended recipe to 110k · running ③ Sharpa co-training at 10 % vs zero-shot · running ④ owner to verify the paired rollout clips.
