Appendix A1 · GR-1 protocol (why H = 4)

Scene
RoboCasa GR-1 tabletop · task PnPCanToBowl · can + bowl in the point set · ego camera
Environment
20 Hz · 720 max steps · 3 episodes · success = the benchmark's own success flag
Execution
synchronous — 4 predicted frames = 8 environment steps = 0.4 s per replan
Why H = 4
it matches GR00T N1.7's official setting for this benchmark exactly (--n-action-steps 8, --max-episode-steps 720); the horizon is theirs, not a choice of ours
Caveat
the zero predictor moves with the checkpoint (3.98–5.03 cm across our reads) because closed-loop truth is the simulator under the model's own actions — per-checkpoint measurements, never a trend

Timestep-matched: the prediction is compared with the simulator at the same environment step, and the zero predictor is that same basis with no motion.

Appendix A2 · DexJoCo protocol & reference points

Scene
hammer_nail · Franka + Allegro · front camera
Environment
50 Hz · 400 max steps (our cap, shorter than the benchmark's) · 3 episodes · success = nail driven ≥ 4 cm
Execution
DexJoCo's own asynchronous rule, copied from their evaluation client: chunk of 10 predicted frames · replan requested when the buffer falls below 80 % · overlapping plans blended · inference latency charged in simulator steps
Latency
pinned at 650 ms so arms differ by model rather than by which node they drew; measured-latency reference reported separately — on the 120M final, pinned 11.35 cm vs measured 11.42 cm, so the pin is not the flattering choice. Scope of that check: the measured run used the new fast decode and drew ~675 ms, so it shows 650 and 675 ms agree — not that the metric is insensitive across the range. The old decode sat near 1090 ms and is not covered by the comparison
Reference
the benchmark's own paper, under object randomisation: π0.5 84.7 % · GR00T N1.5 67.3 % — against our 0 / 3 at every checkpoint

Flat and below zero at every checkpoint; the base's per-epoch column is auto-latency and is not comparable to the pinned arm reads.
