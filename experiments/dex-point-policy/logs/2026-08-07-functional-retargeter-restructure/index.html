Experiment log · Dexterous Point Policy (ICLR 2027)

One frozen human policy, N functional retargeters — idea verified 4/5, design v1 on the table

Restructure of the ICLR-2027 workstream around a human-centric base policy (real human data only, embodiment-free observations) composed with a learned per-embodiment retargeter whose objective is functional: the object must follow the demo's 3D trajectory. Four assigned papers read in full + a 26-work novelty sweep, via 5 parallel reading agents; design v1 written and under discussion.

Verdict

4/5. The architecture is right and mostly de-risked by infrastructure we already validated; the risk concentrates in exactly one place — the retargeter's training signal — because "the object moves the same" is a closed-loop property that cannot supervise a per-step map directly. The fix is pairing-by-outcome: in sim, make each robot hand track each human demo's object trajectory; successes become time-aligned (human ↔ robot) pairs. A 26-work sweep found no 5/5 collision: the claim survives as a conjunction, and the paper hangs on one ablation — the same retargeter trained on kinematic pairs vs object-motion-matched pairs.

01The idea, verified

Proposal: robot policy = RE ∘ πH. πH trained only on human (MANO) data over embodiment-free observations; RE is a small per-embodiment decoder. One base policy, N hands, only the retargeter is embodiment-specific.

Component of the proposalScoreWhy
Motivation (human data as the prior)5/5Standard and in-house-evidenced: W29 (prior irreplaceable, compounds with scale), BMW PT-vs-scratch.
Vision-side embodiment gap4.5/5Already solved by DPP's own design — the policy never sees the embodiment. Enabler, not a claimable contribution (we published it).
Functional definition of retargeting3→4/5Right objective; as stated it is not per-step trainable (closed-loop property). Fixed by pairing-by-outcome + RL fine-tune. Geometric proxy error is measured: ~29 mm median fingertip-vector residual on the easiest hand (Inspire).
Data plan (sim pairs)4/5Sound once rephrased: track each demo's object trajectory per hand in sim; successes = time-aligned pairs. Human side is free (PnP 500 has object clouds + contact per frame).
Experiment plan (openarm-sim)4/5All three hands integrated and smoke-passed; jitter + observation-parity lessons apply to any success-rate claim.

The five sharpenings the idea needs

  • →Object-trajectory equivalence is closed-loop, not per-step.You cannot supervise a_R = R(a_H) with it without rolling out. Resolution: (i) pairing-by-outcome in sim, (ii) RL fine-tune with an object-tracking reward on a geometric prior. Differentiable sim through contact: skip.
  • →The per-step map is ill-posed without context.Same human pose needs different robot joints depending on object geometry and contact state. R_E must be conditioned on (object cloud, proprio, contact) — a small policy, not a converter.
  • →The "hand pose similar" auxiliary is load-bearing, not aesthetic.Pure functional matching admits degenerate grasps that move the object identically but push closed-loop object-in-hand states off the human-data manifold — breaking frozen π_H at the next chunk (the exact DexWAM wrong-attractor failure). Formalize as a small-weight deviation penalty from the geometric retarget. Human2Sim2Robot's ablation independently shows hand-tracking rewards hurt when strong: keep it weak.
  • →Contact is the missing observable.Same object path under different force closure ≠ same robustness. DPP has a contact head — add contact-event timing preservation as a third term.
  • →Deployment needs the inverse map too.π_H consumes human-hand proprio; each embodiment needs R⁻¹ (robot FK → canonical keypoints). Ours exists and is validated; EgoVLA's released equivalent was <0.45 correlation — validate per hand, don't assume.

03Novelty sweep — 26 adjacent works, nothing scored 5/5

Claim at risk: "one frozen human-data policy + N per-embodiment adapters trained without robot demonstrations, closed-loop on ≥3 hands." Four works scored 4/5; each fails at least two legs of the conjunction.

Near-missHasLacks
DexMachina 2505.24853"Functional retargeting" is literally their term: RL tracks demo object states; decaying virtual-object-controller curriculum; 6 hands incl. Inspire.One policy per demo per hand — no reusable module, no human-data base, state-based. → our data engine + strongest mandatory baseline. Also: underactuated hands hardest → Inspire is the stress case.
DexTrack ICLR25Sim-generated (reference→action) pairs → reference-conditioned neural controller; RL+IL flywheel.Pairing is pose-space (kinematic), no frozen-base/adapter split, one hand per system. → our training-recipe template.
EgoScale 2602.16710Frozen 20k-hr human-video VLA + per-embodiment MLP adapters; uses Sharpa. Closest structure.Adapters need 54 h of aligned human-robot teleop play; 2 hands; pure imitation. → our headline economics contrast: they can't add a hand without robot data.
Latent Action Diffusion 2506.14608Shared latent action space over MANO + robot hands; frozen per-embodiment decoders.Kinematic alignment; decoder is a converter (no closed-loop correction); co-trained on robot teleop. → ablation arm.

What makes it unambiguous

  • →Lead with the pairing mechanism.Formalize functional (object-motion-matched) vs kinematic pairing, and run THE ablation: identical retargeter architecture trained on each. If that gap isn't there, the paper isn't there.
  • ·Show the adapter is a policy, not a converter.Perturbation-recovery probe (mid-rollout force pushes) that a DexPilot/GeoRT-class converter structurally cannot pass.
  • ·Quantify "cheap".Per-new-hand cost (GPU-hrs, params, wall-clock) + hands-scaling curve — the figure EgoScale cannot produce without new robot data.
  • ·Baselines reviewers will demand.dex-retargeting converter (no learning) · learned-kinematic MLP (our stage-0 #28/#29) · DexMachina per-demo RL (oracle) · monolithic per-hand controller (task #30 repurposed — tests the factorization) · adapter WITH a small robot-demo set · ablations: ±hand regularizer, frozen vs finetuned base.

Open decisions (blocking the design doc, not the reading)

  • 1Pair engine.Amortized goal-conditioned tracker (recommended) vs per-demo RL vs SPIDER-MPPI (needs an MJCF asset check for openarm + 3 hands).
  • 2Residual vs direct output for R_E.Residual recommended — bakes in the auxiliary, degrades gracefully to the geometric baseline.
  • 3Which frozen base.Existing PnP FT checkpoint (protocol-v2) vs retraining a clean base first.
  • 4Wrist/arm split.Lean: wrist via canonical transform + arm IK (the morphology gap is not in the wrist); R_E owns fingers + small wrist correction. Alternative: R_E outputs all 7 arm joints.
  • 5Contact channel.Binary 5-finger (existing head) vs HRDexDB-style contact/part maps on the object cloud (richer pairing criterion, more work).
  • 6Scope guard.Retargeter-RL is distinct from residual-RL-on-policy (Seunghoon's), but if it should stay out entirely, supervised+DAgger alone still gives a paper.
