The extractor picked the wrong hand. BMW demos are performed with the left hand, but the pipeline had stored the background right hand that drifts into view — ~55 cm from the objects, never touching them. Every base policy was learning from a hand that never did the task. Root-caused, re-extracted all 60 runs on the actor left hand, and retrained all 7 checkpoints. These supersede the policies in the base log.

Verdict

Two hands are reconstructed per frame; single-hand BMW demos use the left. The DPP extractor defaulted to the first valid slot, which was the operator's right hand resting in the background — mean position ~55 cm from the object centroid, never in contact. Fixed by selecting the actor slot explicitly (DPP_JOINTS_SLOT=1) with the matching HaWoR contact index (DPP_CONTACT_IDX=0, cross-ordered), plus a pre-save assert that flags any run whose hand sits >50 cm from the objects. Re-extracted 60/60 (hand→object 9.6–14.4 cm, zero far-flags), rebuilt the 4 training HDF5s, and retrained all 7 base policies to 100k — all torch-load verified. The CHORD contact study and the hand+object viz both run on this corrected data.

01The bug

The MANO pipeline reconstructs two hands per frame (both operators' hands are in view). BMW is a single-hand, left-hand task; the actor hand is the one that reaches the parts. The DPP extractor selected the first slot with a valid track — which was the background right hand.

Hand slotidentitymean position (BA world)to object centroid
0 (was used)background right[−0.14, −0.46, 0.83]~55 cm — never contacts
1 (actor)left, does the task[0.17, −0.11, 0.67]~11 cm — reaches parts

Consequence: object points, contact labels and action targets were all consistent with each other, so nothing crashed and the data looked plausible — but the hand the policy imitated never touched a part. This is why it was caught by geometry (hand-to-object distance), not by any pipeline error.

02The fix

Explicit actor-slot selection, the cross-ordered contact index, and a loud sanity gate — in extract_alin_dpp.py, env-driven so it stays reproducible.

KnobValueWhy
DPP_JOINTS_SLOT1select the actor (left) hand, not the first valid slot
DPP_CONTACT_IDX0HaWoR single-view orders hands opposite the 4-view fit — actor tactile is index 0
sanity assert>0.5 m ⇒ FAR flagprints hand→object distance per run; loud-fails a wrong-hand pick

The cross-index (mesh/joints actor = 1, tactile actor = 0) is the subtle part: the 4-view MANO fit and the single-view HaWoR contact number the two hands in opposite order. Both were pinned down and asserted, not assumed.
